## Browser capability boundary

Desktop Chrome/Edge at a stable loopback HTTP address or HTTPS are the preferred candidate for native directory access. Ordinary remote HTTP is not a supported secure deployment target. Directory picking requires user interaction; permission cannot be silently obtained at startup. Feature-detect both secure context and picker availability. [Directory picker requirements](https://developer.mozilla.org/en-US/docs/Web/API/Window/showDirectoryPicker).

A directory handle can be stored in IndexedDB, not JSON/localStorage. On reopen, restore it and query read/write permissions; if granted, read automatically, otherwise offer a user-triggered reconnect action. Chrome has persistent-permission options, but permission lifetime is user/browser controlled. Do not promise unconditional automatic reopening. [Chrome permission lifecycle](https://developer.chrome.com/blog/persistent-permissions-for-the-file-system-access-api).

Keep origin, browser profile and port stable: 127.0.0.1 and localhost are different origins; clearing site data or changing profile can remove remembered handles. Directory rename/move/deletion, unplugged disks and OS permission changes need recovery paths. Show folder display name, not an invented absolute path. [Handle storage and access](https://developer.chrome.com/docs/capabilities/web-apis/file-system-access).

file sharing entry: inline app may run, but picker availability, permission persistence and IndexedDB/file-origin behavior must be tested in actual target browser. Do not classify every file URL as insecure, and do not promise stable directory reconnection from a moved HTML file. Prefer existing browser storage/explicit JSON fallback unless the precise file scenario passes a capability probe and restart test.

Safari/iOS: do not offer the native directory-reopen contract as supported. OPFS is browser-private storage, not the user's chosen Finder folder; webkitdirectory input can select files for a one-time read but supplies no reusable write handle. [WebKit OPFS explanation](https://webkit.org/blog/12257/the-file-system-access-api-with-origin-private-file-system/), [OPFS and picker distinction](https://web.dev/articles/origin-private-file-system). A compatible fallback must clearly say manual JSON transfer, not claim folder synchronization.

## Alternatives

| Option | Behavior and trade-off | Fit |
|---|---|---|
| A: browser-native folder adapter | Browser storage remains supported; opt into one workspace directory with reusable IndexedDB handle. Read directory snapshot before initializing application; explicit permission reconnect. No server filesystem access. Requires async startup/save refactor and Chromium capability handling. | Recommended if desktop Chrome/Edge with stable local HTTP is the main environment. |
| B: local Node storage service | Extend local server with explicitly configured data directory and validated workspace read/write endpoints. Node owns atomic replace/locking and backups. Browser UI works across browsers; service must be running. Secure localhost boundary, origin checks, path confinement and user-triggered folder configuration needed. | Recommend instead if Safari support and reliable startup directory reads are mandatory; significant scope increase and no standalone-HTML parity. |
| C: browser storage plus manual directory import/export | Keep browser persistence, add profile editing and explicit backup transfer. Broadest sharing compatibility, lowest scope. No automatic re-read of chosen OS folder or continuous write access. | Fallback or deliberate reduced requirement only; does not fully satisfy the requested automatic directory loading. |

Recommendation is conditional, pending PM's runtime answer. Do not add a backend or desktop wrapper by default. A folder picker is access to that user's computer, not a website-wide shared server folder or cloud backup.

## Proposed safety contracts for option A

These are Developer recommendations requiring product decisions; no code changed.

1. One selected directory holds the entire multi-user workspace, not whichever user happened to be active. Proposed dedicated file `beat-workbench.workspace.json` with format marker, independent schema version, workspaceId, revision, activeProfileId and profiles containing metadata/records/tasks. Product release version and file schema version are separate. Keep the existing per-user v3 backup transfer path distinct.
2. Explicit startup states: resolving source, loading, ready, reconnect required, invalid file, write pending, saved, write failed/conflict. Disable mutations while resolving/loading. Never run initializeProfiles or write defaults to the directory before it is read and validated. A JSON parse/permission failure is an error, never an empty dataset. Switching to browser mode requires a visible user choice; do not silently overwrite folder data from a cached browser snapshot.
3. First selection: existing recognized valid file -> load after preview/count confirmation; missing recognized file -> offer explicit new workspace or copy existing browser users; empty existing file, invalid/unknown schema -> stop without overwriting. Ignore unrelated files; never recursively import every JSON. Preserve the previous workspace and all original localStorage keys until a new-source commit succeeds.
4. Migration is read-only capture of all local profiles/logs/tasks, validate, write new snapshot, close, re-read and verify, then activate source. Never delete local data automatically. Existing file plus old browser data is an explicit choice, not an automatic merge. Existing v1 initialization must not run during this discovery stage. Provide backup export before transition.
5. A queued single writer serializes saves; each operation captures workspace/user identity and generation so a delayed completion cannot write to a newly selected source. Coalesce only when it cannot lose intermediate committed state. Only mark directory saved after write/close succeeds. On failure retain dirty state and offer retry/export; do not say saved to folder merely because a browser recovery snapshot exists.
6. Prevent simultaneous writable tabs for the same workspace using a cooperative same-origin lock and notification. Before writing, compare revision/content fingerprint against last read; conflict stops and preserves both candidates for explicit resolution. Such browser locks do not cover other origins, browser profiles, computers or external editors. Revision checks alone have a race; if strong multi-writer guarantees are required, choose B with proper locking. No automatic last-writer-wins or unsupported universal atomicity claim.
7. Use a recoverable prior snapshot where permitted; validate serialized output before replacing primary file and verify afterwards. Test write interruption. Do not promise power-loss atomicity across files or depend on rename APIs without compatibility testing. Bound backup retention and avoid writing unrelated directory files.
8. Async directory persistence cannot rely on beforeunload/pagehide awaiting writes. Incrementally checkpoint running timer/session state with stable session IDs while active; restore explicitly and deduplicate, or agree to a narrower documented guarantee before implementation. Current synchronous best-effort focus save cannot be copied verbatim into an async adapter.
9. Block data-source changes while focus/meeting/task tracking or unsaved drafts are active, with an action to finish/save first; do not discard or auto-assign them to another workspace. A source change drains/settles the write queue, validates candidate data, then commits atomically in memory. Failed/cancelled selection leaves current source and active user unchanged.

## Rename, avatar and JSON compatibility

- Rename updates profile.name by immutable profile.id, never storage-key/user identity; trim, reject empty, retain existing 30-character input intent and define duplicate naming behavior consistently. Avoid applying the import suffix policy implicitly to editing unless approved. Display with textContent/escaping. Update all user labels and backup filename safely.
- Avatar is optional profile metadata. Decode accepted raster images, cap input size and decoded dimensions, crop/resize/re-encode to a bounded raster thumbnail; reject SVG/remote URLs and corrupt images. Suggested processing targets (not Apple requirements): 256x256 storage image, maximum 200 KB encoded image, input maximum 5 MB and explicit pixel-count cap. Final crop experience and display size are Designer decisions. Circular presentation uses CSS, retaining image square for portability; fallback initials/name and accessible upload/remove labels required.
- Keep binary images out of synchronous localStorage where possible. For portable all-in-one snapshots/JSON, bounded PNG/JPEG data URL is simpler; IndexedDB Blob storage is preferable locally if the adapter explicitly serializes avatar bytes on backup. Object URLs are temporary and must not be persisted. Re-encoding avoids preserving original embedded metadata.
- Propose a new documented backup schema version for avatar-bearing exports, with import support for v3 and legacy arrays (no avatar default), and optional profile.avatar metadata in new backups. New importer validates limits independently, preserves records/tasks and never treats missing avatar as a corrupted user. Old app currently ignores unknown avatar metadata, so old imports can retain name/records/tasks but cannot round-trip avatar; disclose that compatibility is data-subset compatibility, not full downgrade preservation. Exact schema version requires PM approval; do not change product version for this report.
- Directory full-workspace import restores stable IDs within its workspace; user-initiated per-profile JSON import retains existing new-independent-profile semantics. Never merge these two modes unintentionally. Avatar persistence must follow the selected data source and be covered in migrations.
- Apple does not supply one universal Web avatar diameter. Its button guidance discusses hit regions; do not relabel a 44-point hit target as mandatory 44-pixel avatar geometry. Designer should propose platform-appropriate circle sizes/hit areas. [Apple button guidance](https://developer.apple.com/design/human-interface-guidelines/buttons).

## Decisions PM needs before a design spec

Primary browser/OS and HTTP versus double-click entry; whether Safari parity is required; whether selected directory owns all users (recommended); desired behavior when permission is lost; whether browser fallback is explicitly manual; whether automatic read includes detection of changes made externally while the page remains open; whether any multi-device/concurrent writing is expected. The remembered handle does not itself watch the directory.

## Updated scope clarification: broad browser/mobile/file coverage

PM relayed the user's latest requirement to cover mainstream browsers, phones and double-click HTML. This supersedes the earlier assumption that a primary desktop Chromium environment might be sufficient. No implementation or version change is authorized by this update. PM is asking whether the user accepts tiered storage support or requires a local application/cloud service.

Proposed tiered contract, pending user acceptance:

- Capable environments: expose directory mode only after checking actual picker/handle storage capabilities. Remember the handle, attempt startup reads only with valid permission, and request reconnection through a user action when needed. Browser brand alone is insufficient, especially on mobile.
- Other browsers/mobile/file entry: use available browser storage and explicit JSON import/export. Clearly label that this mode does not automatically read/write an arbitrary chosen device folder. If persistence itself fails, show temporary-session status; do not report durable saving.
- Mobile file opening: whether the OS/browser opens a local HTML as an executable page rather than a preview is also environment-dependent. Offer a stable hosted/local-network web entry where available; a phone cannot use the desktop's 127.0.0.1 address. Hosting/access scope is a separate decision, not authorization to deploy now.
- If identical automatic external-folder access in every option is mandatory, the pure standalone Web architecture cannot promise it. Option B serves browsers that can reach the local service, but a desktop Node service accesses the desktop's folder, not a phone's arbitrary folder. A phone-specific native bridge/application would be needed for device-local directory semantics; cloud storage would instead provide account/workspace synchronization, not equivalent automatic device-folder access. Both change scope, privacy and deployment requirements and require an explicit architecture choice.

Recommendation under the broadened scope: tiered Web capability support is the smallest honest approach, but remains unapproved. If the user rejects manual fallback, return to architecture selection rather than claiming a Web API/polyfill can bypass platform permissions. Do not label the feature fully cross-platform until the agreed environment matrix has been independently checked.

## 2026-10-10 Developer diagnosis: folder migration and current-profile edits

Assessment only; no behavior changes, browser actions, or access to 4173 personal data. Checked current production call chains and ran isolated in-memory synthetic probes.

Current folder behavior is partially sufficient: bootstrap choose-folder -> guardSource -> picker -> previewDirectory -> confirmation -> activateDirectory. An empty target receives the complete acknowledged workspace clone, including workspaceId/profile IDs, records/tasks, avatars and sessions; save/readback precede source settings. An existing valid target instead becomes the active workspace; current workspace is NOT copied there. Corrupt targets fail validation. Confirmation explicitly says to use folder data, no merge. In-memory probes confirmed empty-target copy and existing-target adoption. Thus unconditional migration to another folder is a new operation beyond current source-selection semantics, not evidence of a copying defect.

Current profile behavior: resetDraft captures active profile ID; save-profile -> saveDraft -> saveProfileDraft -> controller.commit finds that exact ID and changes only name/avatar. Neither push nor ID generation occurs. Synthetic production-controller probe confirmed profile count, active ID and tasks retained after rename; existing profile.test.mjs also checks record retention/failure. Editing via this button should not create a new user.

Actual code paths that intentionally create another user: app.js create-profile handler generates a new user ID, pushes a profile and assigns empty logs/tasks; importBackup also generates a new user ID, pushes a profile and assigns imported logs/tasks. The visible create button is labelled 新建独立工作区. Record storage keys are based on profile ID, never display name. Possible confusion between current profile-name/save-profile and new-profile-name/create-profile needs reproduction evidence; user-reported duplicate has not been reproduced and must not be called a confirmed bug. A backup import producing another user is current deliberate isolation behavior.

Recommendation for PM scope: retain opening existing folder data as a separate explicit action; add an explicit migrate-current-workspace action if approved. Empty target can reuse current copy/readback path. Existing target needs a deliberate overwrite-or-cancel decision, preserved target recovery, expected fingerprint/revision checks, durable close/readback before switching settings, and no deleting old source. Keep original workspace/profile/session IDs, records/tasks and avatar bytes; no merge or imported-user creation. If destination is the current directory, treat as no-op. UI wording/design belongs to Designer. Decide whether nonempty targets may be overwritten and whether old source remains a usable copy before implementation.

For profile duplication diagnosis, request only the sequence of button labels/steps and whether it followed import or directory selection, without private records. If save-profile itself reproduces a new ID, fix as an original-contract bug with a failing synthetic integration test. Otherwise improve separation between editing current profile, creating a user and importing as another user within approved scope.

Probe note: first synthetic rename fixture used a numeric task ID and was correctly rejected by validation; corrected to a string task ID and production controller save passed. This was a fixture error, not a product regression. No code, package, ZIP, commit or push changed in this assessment.
